## 3. 瓶颈分析（**这一节才是重点**）

### 3.1 第一个瓶颈：单会话行锁串行，不是 CPU

R1 → R2：并发连接 ×5，**吞吐只从 387 涨到 425 条/秒（+10%），P99 却从 164ms 涨到 4563ms（28 倍）**。
而 R2 的峰值 CPU 只有 **38.5%**。

- 如果是 CPU 瓶颈 → CPU 应该跑满，而它没有
- 如果是网络瓶颈 → 本机回环，不存在
- **结论：瓶颈在数据库写路径的串行化**

根因是 `seq` 分配的实现：在**一个事务内**对同一行加排他锁

```sql
BEGIN;
SELECT next_seq FROM conversations WHERE id = ? FOR UPDATE;  -- 行级排他锁
UPDATE conversations SET next_seq = next_seq + 1 WHERE id = ?;
INSERT INTO messages (...) VALUES (...);
COMMIT;
```

所有消息都写同一个会话 → 所有事务抢**同一行** → 完全串行。
单事务约 2.3ms（3 次 DB 往返）→ 理论上限 ≈ 1/0.0023 ≈ **430 条/秒**，与实测的 425 条/秒吻合。

### 3.2 第二个瓶颈：DB 连接池只有 25，超载后大量超时

R3（5000 连接）时出现 **16835 次 `context deadline exceeded`**，日志证据：

```text
level=ERROR msg="ws 消息业务处理失败" user_id=905 err="context deadline exceeded"   ×16834
level=ERROR msg="投递失败：查成员列表出错" conversation_id=378 err="context deadline exceeded"  ×3101
```

根因在 `server/internal/store/db.go`：

```go
maxOpenConns = 25   // 最大打开连接数：本地单机 + 单人用，25 足够
```

25 个数据库连接要服务 5000 个并发发送者。每个发送需要：
① 一个连接做 `SELECT ... FOR UPDATE` 事务（持有到 COMMIT），② 投递时再查一次成员列表。
排队等待时间超过了 WebSocket 请求的 context deadline → 请求被取消 → 返回错误信封。

> MySQL 侧 `Max_used_connections = 29`（< `max_connections = 151`）——
> **不是 MySQL 拒绝连接，是我们自己的连接池太小。**
> Redis `maxclients=3168` 也**没有**成为瓶颈（压测期间 Redis 连接峰值仅 75）。

### 3.3 5000 并发长连接本身完全没问题

R4 专门测"连接容量"：每连接发 0 条消息，建立后保持 25 秒。

- **5000 / 5000 连接同时在线**（`/healthz` 的 `wsConnections` 峰值 = 5000）
- 峰值 CPU 仅 **2.2%** → 每连接 **0.044%**
- 峰值堆 **98.3 MB** → 每连接约 **20 KB**
- goroutine 9 → 10009（连接 × 2 个读写协程，符合设计）→ 断连后回落到 **87**

> **结论：网关层能扛 5000 并发长连接，且断连后资源完全释放（无泄漏）。**
> 瓶颈不在连接数，而在**高并发写入时的 DB 连接池与锁竞争**。

## 4. 如果继续优化，下一步做什么

| 优化 | 预期收益 | 代价 |
| --- | --- | --- |
| **① 把 `maxOpenConns` 从 25 提到 100~200** | 直接消除 R3 的 `context deadline exceeded` | MySQL 每连接约 200~500 KB 内存；需同步调 `max_connections` |
| **② `seq` 分配改成 Redis 预分配区间**（一次取 100 个号） | 消除单会话行锁，吞吐可提升一个数量级 | 序号可能因进程崩溃出现**空洞**（本项目已接受"seq 单调不连续"的语义，代价可控） |
| **③ 投递时的成员列表加本地缓存**（TTL 5~10s） | 减少每消息一次的 DB 查询 | 群成员变更最多延迟 TTL 生效 |
| **④ 群聊投递批量化 / 只推在线成员** | R3 的 push 数达 103 万，扇出开销显著 | 实现复杂度上升 |

> 本次压测只做到"发现问题"，**没有做上述优化** —— 因为这是个人项目，
> 当前瓶颈发生在 5000 并发这种极端场景，而目标是证明**架构和一致性正确**。
> 优化方向写在这里，作为下一步的技术债说明。

## 6. 连接池调优实验（**A/B 实测，结论和预期相反**）

### 6.1 改了什么

之前 §3.2 把「`maxOpenConns = 25`」列为第二瓶颈。这一轮把它做成**可配置**：

| 改动 | 内容 |
| --- | --- |
| 环境变量 | `DB_MAX_OPEN` / `DB_MAX_IDLE` / `DB_CONN_MAX_LIFETIME_MIN` |
| 默认值 | 仍然 25 / 10 / 3 —— **不设环境变量时行为完全不变** |
| 安全夹取 | `0` 在 `database/sql` 里表示"无限制"（会把 MySQL 打死），所以非法值回落默认；上限 1000；idle 不超过 open |
| 可观测性 | `/healthz` 新增 `pool.{maxOpenConns,openConns,inUse,idle,waitCount,waitDurationMs}` —— **`waitCount` 就是"有多少次被迫等连接"** |
| 测试 | 8 个单测覆盖默认值 / 零值 / 负数 / idle>open / 上限 / 显式值 / nil 安全 |

### 6.2 实验结果（同一台机器，参数一致，背靠背跑）

**1000 并发 × 10 条**

| 指标 | 池 25（默认） | 池 150 | 变化 |
| --- | --- | --- | --- |
| `waitCount`（等连接次数） | **37207** | **17492** | **↓ 53%** |
| 吞吐 | 396.53 /s | 395.86 /s | **−0.2%（无变化）** |
| P99 | 7038.52 ms | 6574.85 ms | −6.6% |
| 峰值 CPU | 39.1% | 39.4% | ≈ 0 |
| ack | 10000 / 10000 | 10000 / 10000 | 都零丢失 |

**5000 并发 × 5 条**

| 指标 | 池 25 | 池 150 | 变化 |
| --- | --- | --- | --- |
| ack | 8165 / 25000 | **6231 / 25000** | **−23.7%（更差）** |
| 错误信封 | 16835 | **18769** | 更多 |
| 吞吐 | 138.34 /s | 123.80 /s | **−10.5%** |
| P99 | 25080.69 ms | 19864.40 ms | −20.8% |
| 峰值池占用 | 25 | 150 | — |

### 6.3 结论：**调大连接池解决不了这个问题**

**1000 并发**：`waitCount` 确实降了一半（3.7 万 → 1.7 万），说明连接池确实是瓶颈之一。
但**吞吐一点没涨，P99 只降 6.6%** —— 因为主瓶颈是 §3.1 那个**单会话行锁串行**，
连接多了只是让更多事务同时在 MySQL 里排队抢**同一行**。

**5000 并发反而更差**（ack −23.7%）。原因是：

> 把队列从 **Go 的连接池**（便宜、快、FIFO）搬到了 **MySQL 的行锁等待**（贵、慢、持有连接不放）。
> 150 个事务同时抢同一行，每个都要把连接占住直到拿到锁，
> 于是连接池从"排队点"变成了"锁竞争的放大器"。

**这修正了我上一版报告的判断**：连接池不是"第二瓶颈"，它是**放大器**；
真正的根因只有一个 —— **单会话写入被 `FOR UPDATE` 完全串行化**。

### 6.4 那正确的优化方向是什么

| 方案 | 能否解决 | 代价 |
| --- | --- | --- |
| **seq 改 Redis 预分配区间**（一次取 100 个号） | ✅ 真正的解法：把「事务内抢行锁」变成「进程内自增」 | 序号可能出现更大空洞（本项目已接受「seq 单调不连续」语义）；进程崩溃会浪费一段号 |
| 分片（不同会话写不同表 / 不同库） | ✅ 能绕过单行锁 | 复杂度高，跨会话查询变难 |
| 调大连接池 | ❌ **实测无效甚至更差** | 占用更多 MySQL 内存 |
| 加机器 | ❌ 瓶颈在单行锁，加机器不解决 | 成本 |

> **这次实验最大的价值是「证伪」**：我原本以为调大连接池能改善，
> 实测发现只是把排队位置换了地方，高并发下还更差。
> **写进简历/面试时，这种"试了但没用的优化 + 为什么"比"我做了优化"更有说服力。**
