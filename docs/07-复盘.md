## 2. Bug 复盘（按「教训价值」排序）

### 2.1 【最严重】幂等占位不释放 → 消息永久发不出去且不报错

**现象**：某条消息一直发不出去，客户端反复重试，**不报错、也不成功**，直到 5 分钟后自己好了。

**根因**：三层幂等的第 ① 层用 Redis `SETNX` 占位（`Placeholder`）。
如果落库失败（比如 DB 抖动），代码没有 `Release` 这个占位 ——
后续每次重试都读到 `Placeholder`，被判定为「另一个请求正在处理」，
于是返回「处理中」，客户端继续重试，形成 **直到 TTL 到期才自愈的死循环**。

**修法**：落库失败路径**必须** `Release`。代码里现在有显式注释警告这一点。

**教训**：**分布式锁/占位类设计，释放路径和获取路径同等重要。**
而且这种 bug 不会报错 —— 它会表现为「用户说发不出去，但日志里全是正常」。
排查时应该盯 `Placeholder` 的 TTL 和 `Release` 的调用次数。

### 2.2 AI 消息复用「不推给发送者」的规则 → 发起者永远收不到 AI 回复

**现象**：在聊天里发 `@AI 总结一下`，AI 回了，但**只有对方能看到**，自己看不到，必须刷新。

**根因**：普通消息的投递规则是「不推给发送者」——因为发送者本地已经乐观显示了一条。
AI 消息复用了这个规则，但 AI 消息是**服务端生成**的，请求者本地**什么都没有**。

| | 普通消息 | AI 消息 |
| --- | --- | --- |
| 谁生成 | 客户端 | 服务端 |
| 发送者本地 | 已有乐观显示 | 没有 |

**修法**：拆出 `deliverToAll`：
```go
func (s *MessageService) deliver(ctx, msg)      { s.deliverExcept(ctx, msg, msg.SenderID) }
func (s *MessageService) deliverToAll(ctx, msg) { s.deliverExcept(ctx, msg, 0) } // 0 不是合法 ID
```

**教训**：**复用一条规则之前，先确认它的前提条件在新场景下还成立。**
这个 bug 是验收脚本「让发送者等自己的 AI 回复」超时 30 秒暴露出来的 ——
**如果只做「人工点一下看不报错」的验收，永远发现不了。**

### 2.3 已读人数把发送者算进去了 → 「刚发出的消息显示已读 1/4」

**现象**：群聊里刚发出一条消息，下面立刻显示「已读 1/4」。那「1」就是自己。

**根因**：`已读 N/M` 的分母取了群成员总数，分子是 `lastReadSeq >= seq` 的人数。
但 **发消息不会推进发送者自己的 `last_read_seq`**（已读是客户端收到 ack 后才上报的独立动作）。

**修法**：只统计**接收者**（排除发送者）。4 人群里 A 发出、B 读过 → 「已读 1/3」。

**教训**：「数字看着对、含义错了」是最难发现的一类 bug。
**必须真的跑起来看界面**，而不是只看接口返回 200。

---

### 2.4 Nginx 默认 60 秒断开 WebSocket，且日志里没有错误

**现象**：本地一切正常；部署后能连上，但**挂 60 秒不动就断**，Nginx 日志里没有 error。

**根因**：`proxy_read_timeout` 默认 60 秒。长连接超过 60 秒无数据被**静默断开**。

**修法**：`proxy_read_timeout 300s;`（必须大于客户端心跳 25 秒）。
同一批还有另外两个必配项：`Upgrade`/`Connection` 头（否则握手 400）、`proxy_buffering off`（否则消息被攒着延迟发）。

**教训**：**「多久之后才出问题」的 bug 最难查**，因为它看起来像业务逻辑问题。
记住三个数：**Upgrade 头、60 秒、buffering off**。

### 2.5 MySQL 连接被服务端中断 → 连接池里有死连接，请求 500

**现象**（本轮实测）：`KILL` 掉应用在 MySQL 上的连接后，**下一个 HTTP 请求立刻 500**：
```
level=ERROR msg=请求处理出错 path=/api/v1/auth/login status=500
  error="查询用户失败: invalid connection"
```
之后连接池自动重建，`/healthz` 恢复 `mysql=ok`，消息发送恢复正常。

**根因**：`database/sql` 的连接池会把死连接发给请求；
`go-sql-driver` 的 `invalid connection` 不总是被翻译成 `driver.ErrBadConn`，所以不会自动重试。

**修法（已做）**：`SetConnMaxLifetime(3*time.Minute)` 让连接定期轮换，缩短死连接的存活窗口。

**下一步**：可以对 `invalid connection` / `ErrBadConn` 做一次显式重试（幂等操作安全）。

**教训**：**「服务不崩」和「请求都成功」是两件事。**
故障演练要同时记录「服务是否活着」和「用户请求的成功率」。

### 2.6 【安全】发布脚本把含真实密码的迁移文件打进了发布包

**现象**：检查发布包内容时发现 `migrations/local/000_bootstrap.local.sql` —— 里面有 **32 字符真实数据库密码**。

**根因**：`release.ps1` 用 `Copy-Item -Recurse` 拷整个 `server/migrations`，
而 `migrations/local/` 只是靠 `.gitignore` 保护，**打包脚本不认识 .gitignore**。

**修法**：只拷顶层 `*.sql`；并加**密钥扫描门禁**——包里出现硬编码密码 / `sk-` key / `*.local.sql` 一律拒绝打包。

**教训**：**`.gitignore` 只保护 git，不保护你的发布流程。**
任何「把仓库内容打包上传」的脚本都必须自己有敏感文件清单。

### 2.7 验收脚本自己的 bug，比被测代码的 bug 更多

这是本项目最反直觉的发现。**验收脚本本身出过至少 5 次错，每次都伪装成产品 bug**：

| # | 脚本 bug | 被误判成什么 | 真相 |
| --- | --- | --- | --- |
| 1 | 裸 `ReceiveAsync` 取到 `presence` 而非 `send_ack` | 离线序号错位 | 消息类型没过滤 |
| 2 | `CancellationTokenSource.Cancel()` 取消后整个 WS 不可用 | 「服务端断开了我的连接」 | 自己把 socket 废了 |
| 3 | 用 2.5 秒超时断言「不该收到」 | 「退群后仍收到消息」 | 超时把 socket 标记为 broken，后续全废 |
| 4 | 断言前没排空积压的 push | 「D 退群后收到 seq=2」 | 拿到的是退群**之前**的旧消息 |
| 5 | `next_seq = 1` 清空压测会话 | 「seq 有缺口，丢消息了」 | `next_seq` 语义是「最后分配的 seq」，应为 0 |

**教训**：
**验收脚本必须和被验收的代码一样严谨。**
一个好习惯是：**先让脚本在「确定的正常状态」下全绿，再去制造故障** ——
否则你分不清失败是产品坏了还是脚本写错了。

### 2.8 环境踩坑清单：PowerShell 5.1 按 ANSI 读无 BOM 的 UTF-8（**踩了 6 次**）

这个坑在本项目里出现了 **6 次**，每次都表现为不同症状，值得单独记一笔：

| # | 症状 | 后果 |
| --- | --- | --- |
| 1 | `Select-String -Pattern '中文'` 匹配不到 | 误判配置「已填」 |
| 2 | `.env` 里中文密码长度算成 30（实际 51） | 误报配置正确 |
| 3 | `.ps1` 里中文注释 → `Unexpected token '}'` | 脚本语法错误 |
| 4 | 脚本里硬编码 `'小王'` 断言恒为 false | 验收假失败 |
| 5 | 采样器中文注释 → **语法没错但行为错了**（不写数据行） | 压测峰值为 0 |
| 6 | 命令里用中文引号 `“ ”` → 解析失败 | 检查脚本报错 |

**同一条规矩永远适用**：**生成的 `.ps1` 文件保持 100% ASCII**；
需要中文就写进 `.md` 或用 UTF-8 BOM 保存。

其他环境坑：
- **esbuild.exe 只有 2.36 MB**（正常 9.45 MB）—— 上次安装被中断留下损坏的 tarball 缓存。
  `npm cache clean --force` + 删 `node_modules` 重装。
- **esbuild 无法删除系统 temp 里的自身副本**（`Access is denied`）→
  `ESBUILD_BINARY_PATH` 无效，把 `TEMP`/`TMP` 指到工作区内解决。
- **nginx for Windows 不支持中文路径**（用 ANSI 码页）→ `nginx -t` 必须放在纯 ASCII 路径下跑。
- **`/healthz` 的 `cpuSeconds` 在 Windows 上恒为 0** → 一度算出 1114% 的荒谬 CPU 值。
  已把该字段删除 —— **宁可没有，也不给一个假数字。**

## 3. 故障演练（全部实测）

### 3.1 杀服务进程：客户端 3.2 ~ 6.4 秒自动恢复

用 `server/cmd/wsprobe`（**复刻前端的退避策略** 1→2→4→8→16→30s ±20%）实测三次：

| 轮次 | 服务端重启耗时 | 客户端恢复可用 | 重连尝试 |
| --- | --- | --- | --- |
| 1 | 3.60 s | **6.37 s** | 3 |
| 2 | 3.47 s | **3.22 s** | 2 |
| 3 | 3.43 s | **3.43 s** | 2 |

波动原因：恢复时间 = 服务端拉起时间（≈3.5s）+ **落在哪个退避档位**（1s / 2s / 4s）。

### 3.2 停掉 Redis：消息仍然成功（但延迟 +3 秒）

| 观察项 | 实测结果 |
| --- | --- |
| 服务是否存活 | ✅ 存活，`/healthz` 报 `status: degraded, redis: error` |
| 消息是否成功 | ✅ 成功（`send_ack`，seq 递增） |
| 日志 | ✅ `level=WARN msg="幂等缓存不可用，降级到数据库唯一索引"` |
| 日志 | ✅ `level=WARN msg="写幂等结果失败（不影响正确性）"` |
| **延迟** | ⚠️ **从 ~5ms 变成 3036ms**（go-redis 连接被拒后重试的开销） |
| Redis 恢复后 | ✅ 自动回到 `ok`，**不需要重启服务** |

> **这是本次演练最有价值的发现**：设计上「Redis 是加速器不是正确性依赖」是对的，
> 但**体感上 Redis 挂掉不是「没影响」，而是每条消息慢 3 秒**。
> 优化方向：调小 go-redis 的 `MaxRetries` / `DialTimeout`。

### 3.3 KILL 掉 MySQL 连接：下一个请求 500，池自动重建

| 观察项 | 实测结果 |
| --- | --- |
| 服务是否存活 | ✅ 存活 |
| 下一个请求 | ❌ 500 `查询用户失败: invalid connection` |
| 之后 | ✅ 连接池自动重建，`/healthz` 回到 `mysql=ok` |
| 再发消息 | ✅ 成功（`send_ack`） |

详见 §2.5。

### 3.4 补充：Nginx 三个 WebSocket 坑做了真实验证

部署物料里的 `deploy/nginx/im-chat.conf` 原本只做了语法校验（`nginx -t`）。
后来用本机 Windows 版 nginx + 仓库里的**真配置**做了一次完整验证
（脚本：`deploy/local/verify-nginx-local.ps1`，**18/18 PASS**）：

| 坑 | 验证方式 | 结果 |
| --- | --- | --- |
| #1 缺 `Upgrade` 头 | 让一条 WS 连接穿过 nginx | 握手 `Open`，access.log 里 `"GET /ws" 101 338` |
| #2 缺 `proxy_read_timeout` | **空闲 70 秒**再发消息 | 连接存活，收发正常 |
| #3 缺 `proxy_buffering off` | 测 send/ack 往返 | 21~49 ms |

还用 `localhost.run`（SSH 隧道，无需注册）做了**公网验证**：

| 验证 | 结果 |
| --- | --- |
| 公网 HTTPS 首页 | 200，页面正常 |
| 公网 API | `code=0` |
| **公网 WSS 握手** | `wss://…lhr.life/ws` → Open |
| 公网消息往返 | `send_ack` 递增，697 ms |
| 公网空闲 70 秒 | 连接仍存活 |

> ⚠️ **这证明的是「配置正确 + 公网能访问」，不是「部署到云服务器」。**
> 隧道地址是临时的，也不验证 systemd / 域名 / 长期稳定性。
> **这条边界必须说清楚，不能拿它当"已上线"。**

## 4. 性能瓶颈（实测定位，不是猜的）

| 瓶颈 | 证据 | 结论 |
| --- | --- | --- |
| ① 单会话 `FOR UPDATE` 行锁串行 | 200→1000 连接，吞吐只 +10%（387→425/s），P99 却 ×28（164→4563ms），**CPU 仅 38.5%** | 不是 CPU 瓶颈，是写入串行化。上限 ≈ 430 条/秒（单事务 ~2.3ms） |

## 5. 如果重做，我会改什么

1. **更早做压测** —— 瓶颈（连接池 25 + 行锁）从一开始就存在，第 13 周才发现，改动成本更高。
   **性能验证应该跟着功能走，不是攒到最后。**
2. **更早加可观测性** —— `/healthz` 的 goroutine / 堆指标是压测时才加的。
   在此之前排查「连接关了但资源没释放」只能靠猜。
3. **验收脚本先自测再测产品** —— 见 §2.7，脚本 bug 浪费的时间比产品 bug 多。
4. **把 `.env.example` 的每个键和 `config.go` 做自动比对** ——
   这次是靠手工 grep 对齐的，容易漏。
5. **给 `invalid connection` 加重试** —— 见 §2.5。

## 6. 诚实的局限（面试主动说，别等被问）

| 局限 | 说明 |
| --- | --- |
| **没有正式公网地址** | 部署物料（systemd/Nginx/发布/回滚/备份/验收）已全部就绪；Nginx 的三个 WebSocket 坑已用**本机 nginx + 真实配置**逐条验证（18/18 PASS），并用 SSH 隧道做过公网访问验证（HTTPS + WSS + 空闲 70 秒均通过）。**但没有部署到云服务器**，所以 systemd / 域名 / 长期稳定性都没验证，「已上线」这条不算完成。 |
| **压测是同机** | 客户端与服务端在同一台笔记本上争抢 CPU，数字是「本地单机上限」，不代表生产环境。 |
| **没有调优** | 连接池仍是 25，行锁仍是行锁。瓶颈如实记录为技术债。 |
| **AI 是 mock 模式** | 没有真实大模型 key，所有 AI 输出都带 `[MOCK]` 标记，**不代表模型能力**。真实调用代码已写好并单测覆盖，但未经真实调用验证。 |
| **没有 HTTPS** | 只有 IP 无域名时无法签证书；此时 WS 是 `ws://`，token 走 query 明文传输。 |
| **发布有秒级中断** | 单实例重启。客户端会断线重连（实测 3.2~6.4 秒恢复），但不是真正的零停机。 |
| **单机** | 没有主从、没有负载均衡。`Restart=always` 能兜住崩溃，兜不住宕机。 |

## 附：前端可用性与视觉改造（第 12 轮追加）

这一轮不是加功能，是**修一个真实缺陷 + 学一套设计评审方法**，结论对面试有用。

### 1. 真实缺陷：手机端根本不能用

改造前用 Chrome DevTools Protocol 在 375×812 视口实测：

| 元素 | 宽度 |
| --- | --- |
| `.side`（会话侧栏） | 288px（写死） |
| `.main`（聊天区） | **87px** |
| `.main` 内容所需宽度 | 274px（只给 87px，被裁掉） |

截图里聊天标题被压成**竖排单字一列**。这不是审美问题，是**功能性缺陷** ——
而面试官用手机点简历链接是大概率事件。

**修法**：手机上改成 master-detail 两屏（列表 / 聊天），点返回只切换显示、不改 `activeConvId`
（不退订、不清消息、不重拉历史）。桌面端靠媒体查询完全隔离，实测布局无变化（288 + 1152）。

**结果**：聊天区 87px → **375px**，横向溢出 0px，桌面端 0 回归。

### 2. 用设计评审工具代替「我觉得好看」

引入开源 skill「design-taste-frontend」做两件事：

1. **它自带测量器**（`inspect.mjs` / `lint.mjs`），把「好看」变成可数的指标：
   渐变数、阴影数、细线数、装饰编号数、字号档位、图片数、动效元素数、对比度、空白带……
2. **它区分两类界面**：落地页（读的，允许大字号与留白）vs 应用屏（用的，标题 18-32px、不许空白带）。
   这个区分很关键 —— 把珠宝官网那套套到聊天界面上，只会让它更难用。

**实测改善**：

| 界面 | 改造前 | 改造后 |
| --- | --- | --- |
| 登录页 | 2 FAIL（渐变背景、卡片重阴影） | **0 FAIL** |
| 聊天页 | （未测量，无工具） | **0 FAIL / 0 WARN** |
| 源码 lint | 7 FAIL（emoji、渐变） | **0 FAIL** |

其中最有价值的一条发现：**Element Plus 默认主色 `#409eff` 没有被覆盖**，
于是屏幕上同时存在品牌深蓝与 EP 亮蓝两套强调色，且亮蓝在白底上只有 **2.8:1** 对比度。
这种问题**只看代码发现不了**，只有测量才发现。

### 3. 动效：先定边界，再写代码

app screen 的规则是「动效只做反馈（按压/悬停/焦点/行到达/面板打开），屏幕不做入场动画」。
所以只做了四类，其中只有「新消息行到达」用 GSAP（需要按 key 定位 + 连续到达时覆盖 + 结束清内联样式），
其余用 CSS。并做了**双层 reduced-motion 降级**（CSS 压时长 + JS 直接不创建 tween）。

**验证方式**：CDP + MutationObserver 观察 `.msg-row` 的 `style` 变化 ——
正常模式捕获到内联 transform/opacity（动画真的在跑），`reduce` 模式 0 次（正确跳过）。

### 4. 踩过的坑（都是真金白银的时间）

1. **多段构建流水线会静默失败**：`npm run build` 实际是 `vue-tsc --noEmit && vite build`。
   模板里残留一个已删除的字段（`{{ s.k }}`）让 type-check 失败，**build 没产出新产物**，
   而我把旧 `dist` 同步到了 nginx —— 于是「改了没生效」，白查一整轮。
   **教训：这类命令必须逐段检查退出码，不能只看有没有输出 `built in`。**
2. **样式补丁会落进错误的块**：往已有多行 CSS 里插入规则时，按行尾匹配经常不命中，
   结果「✅ 替换成功」是假的。**可靠做法：在样式末尾追加独立媒体查询块**（后写优先），不要改旧块。
3. **改文件前先确认它真的被引用**：删 `:root` 变量时一并删掉了别处在用的 `--im-primary-light`，
   导致头像圆圈消失 —— 是从截图里发现的，不是从代码里。

### 5. 一次「及时止损」的判断（比技术更值得说）

中途做了一版「产品首页」（杂志编辑风格落地页），跑闸门修到 0 FAIL，花了十几轮。
然后回头问了一个问题：**它对我的投递目标有必要吗？**

结论是**没有**：

- 校招技术面问的是 seq 分配、幂等、断线恢复，不会评价落地页排版；
- 页面上所有有分量的东西（截图、压测数字、链路）**都来自应用本体**，
  落地页本身只是排版 + 文案 —— 恰恰是 AI 时代最不稀缺的东西；
- 它还有维护成本（截图要重截、数字要跟代码同步）。

**于是删掉了**（路由、页面、素材、字体请求全部移除，构建产物已确认无残留 chunk）。
把力气留给真正决定成色的东西：**正式公网部署**、**真实 LLM key 跑通 real 模式**。

> 这条写进复盘，是因为它体现的是**判断力**：
> 能把一件事做到 0 FAIL，也能在发现它不值时果断删掉。
