## 一、项目章程

### 1.1 背景（为什么做这个）

| 项 | 内容 |
| --- | --- |
| **问题** | 简历上的项目经历无法证明「我能独立交付一个系统」——课程设计规模太小，且是小组作业，无法说清自己负责了什么 |
| **机会** | 即时通信（IM）是少数几个**一个人也能做完整、且技术深度足够被追问**的题材 |
| **为什么是 IM** | 它天然包含有状态长连接、可靠投递、顺序保证、离线同步、并发一致性——这些是后端面试的核心考点，**而且能用压测量化** |

### 1.2 目标（可验收）

| # | 目标 | 验收标准 | 状态 |
| --- | --- | --- | --- |
| G1 | 交付一个**公网可访问**的 IM 应用 | 面试官能用浏览器打开链接并完成一次真实对话 | ⬜ |
| G2 | 单聊消息**不丢、不重、不乱序** | 弱网重试下 1000 条连续消息在库里正好 1000 条、seq 连续无重复 | ⬜ |
| G3 | 断线后可恢复 | 关掉浏览器 5 分钟后重开，消息自动补齐 | ⬜ |
| G4 | 有**可量化**的性能证据 | 至少 1 个实测数字：并发连接数 / P99 延迟 / 消息零丢失 | ⬜ |
| G5 | 代码与过程可被检验 | 仓库有 ≥ 14 周提交历史、CI 全绿、README 能让人 5 分钟跑起来 | ⬜ |
| G6 | 我自己能讲清每一处设计 | 关掉代码，10 分钟口述完整链路 + 3 个取舍 | ⬜ |

### 1.3 **非目标**（明确不做什么）

> 这一节比「目标」更重要。零基础最容易犯的错是范围失控——什么都想做，最后什么都没做完。

| # | 不做 | 为什么 | 面试怎么答 |
| --- | --- | --- | --- |
| N1 | 移动端 App（iOS / Android） | Web 端已足够证明能力，移动端引入平台相关的坑，性价比低 | 「Web 端已能证明端到端能力，移动端是平台适配问题，不是架构问题」 |
| N2 | 实时音视频通话 | 音视频必须外购 SFU，自研不可行 | 「我前期调研过 webrtc-rs，官方承认 111 KiB/连接的内存泄漏，**自研 SFU 当前不可行**」 |
| N3 | 端到端加密（E2EE） | 涉及密钥管理、多设备一致性、合规，工作量远超收益 | 「我知道 Signal 协议的原理，但它需要跨端一致的密码学实现，超出单人 14 周的范围」 |
| N4 | 消息撤回 | 纯增量功能，面试提问价值最低 | 「优先级让给了群聊与已读回执，因为它们涉及投递扩散和状态同步，技术含量更高」 |
| N5 | 微服务拆分 | 一个人一个进程足够，过早拆分会放大调试成本 | 「我先用模块化单体把边界划清，等真出现独立扩缩容需求再拆」 |
| N6 | Kubernetes | 同上，运维复杂度远超收益 | 「K8s 不是 IM 的门槛，是团队规模的门槛」 |
| N7 | 朋友圈 / 动态 / 支付 | 与「即时通信」核心能力无关 | — |
| N8 | 离线推送（APNs / 厂商通道） | 没有移动端就不需要；国内厂商通道是出了名的坑 | 「国内 6+ 家厂商通道没有统一协议，且 Flutter/非 Java 服务端 SDK 支持不一」 |
| N9 | 追求「恰好一次」投递 | 分布式下代价过高 | 「用『至少一次 + 幂等去重』等价实现，**代价可控**」 |

### 1.4 干系人

| 角色 | 是谁 | 关心什么 |
| --- | --- | --- |
| 交付者 | 邱漫 | 4 个月内拿到可写进简历的作品 |

## 二、需求：用户故事与验收条件

格式：**作为〈角色〉，我想要〈功能〉，以便〈价值〉**

### Epic 一览

| Epic | 用户故事 | 优先级 |
| --- | --- | --- |
| **E1 账号** | 注册账号 / 登录 / 设置昵称头像 | Must |
| **E2 好友** | 搜索用户 / 添加好友 / 查看好友列表 | Must |
| **E3 单聊** | 发消息 / 看历史 / 知道发送成功 / 断网后补收 | Must |
| **E4 会话** | 会话列表与最后一条消息 / 未读数 | Must |
| **E5 群聊** | 建群拉人 / 群内看到发送者 | Should |
| **E6 已读** | 知道对方读没读 | Could |
| **E7 AI** | 在会话里叫 AI 总结 | Could |
| **E8 运维** | 知道服务是否健康 | Should |

### 关键验收条件（Given / When / Then）

**E3-1 不丢不重不乱序**

```text
Given  我已登录，且与好友 A 有一个会话
When   我连续发送 1000 条消息，期间人为断网 3 次（每次 5 秒）
Then   数据库中该会话的消息总数正好 1000 条
  And  该会话的 seq 从 1 到 1000 连续、无重复、无空洞
  And  界面上最终显示的消息顺序与发送顺序一致
  And  断网期间发送的消息，在恢复网络后全部送达且只有一份
```

**E3-2 离线补拉**

```text
Given  我关闭浏览器
When   好友 A 给我发 20 条消息
  And  我 5 分钟后重新打开浏览器
Then   我能在 3 秒内看到这 20 条消息，顺序正确
  And  服务端只为这 20 条消息计算了一次增量（不重复推送全量历史）
```

**E3-3 幂等（重复发送）**

```text
Given  我发出一条消息但没收到 ack
When   客户端用同一个 client_msg_id 重发 3 次
Then   服务端三次都返回同一个 seq
  And  数据库中该 client_msg_id 只有 1 条记录
```

**E4-1 未读数**

```text
Given  会话最新 seq = 10，我的 last_read_seq = 0
Then   未读数显示 10
When   我上报已读 seq = 6
Then   未读数显示 4
  And  若随后收到乱序的「已读 seq=5」，已读位置不回退（仍为 6）
```

**E5-1 群消息投递**

```text
Given  我在一个 4 人群里
When   我发一条消息，其中 3 人在线
Then   3 个在线成员都实时收到
  And  界面显示发送者昵称与头像
  And  已读状态按人数统计（如「已读 2/4」）
```

**E6-1 已读回执**

```text
Given  群里有 A、B、C、D 四人
When   A 读到 seq=10
  And  B 上报自己读到 seq=10
Then   B 的界面对该消息显示「已读」
  And  A 能看到该消息的已读人数
```

## 三、MoSCoW：MVP 范围

| 级别 | 含义 | 本项目内容 |
| --- | --- | --- |
| **Must** | 不做就不算交付 | 注册登录、好友、单聊收发、会话列表、历史分页、**不丢不重不乱序**、断线重连与补拉、健康检查、部署上线 |
| **Should** | 应该做，时间不够可延后 | 未读数、群聊、头像、优雅退出、结构化日志、CI |
| **Could** | 有余力再做 | 已读回执、AI 助手、全文搜索 |
| **Won't** | 这一版明确不做 | 见 §1.3 的 9 条 |

### MVP 的一句话定义

> **两个用户能在公网上的浏览器里，稳定地互相发消息；断网恢复后不漏消息；我能拿出一个压测数字。**

只有这句话全绿，才算 MVP 完成。其余都是加分。

### 范围控制规则（写在墙上）

1. **任何新想法先写进「Could」列**，不要当场实现。
2. **每个 Sprint 结束才允许重新排优先级**，中途不改范围。
3. **如果某周落后了，砍的是「Could」，不是「Must」。**
4. **加功能之前先问：这个功能面试官会问吗？** 不会问的，不加。

## 四、排期与 Sprint 验收

前提：**每天 4 小时**，每周 6 天 ≈ 24 小时/周。

| Sprint | 周 | 主题 | 验收（可测） | 状态 |
| --- | --- | --- | --- | --- |
| **S0** | 1–2 | 立项 + 设计 + Git 打通 | 本文档 + 架构/ER/接口契约完成；仓库可打开；首个 PR 已合并 | 🔄 |
| **S1** | 3 | 账号与鉴权 | `curl` 完成 注册→登录→带 token 访问；密码在库里是 bcrypt 哈希 | ⬜ |
| **S2** | 4–5 | 长连接网关 | 两客户端连上同一网关；看到对方在线；拔网线 10 秒后自动重连 | ⬜ |
| **S3** | 6–7 | 单聊可靠投递 | §2 的 E3-1 / E3-2 / E3-3 三条全绿 | ⬜ |
| **S4** | 8–9 | 前端 Vue 3 IM UI | 两浏览器窗口互发成功；刷新后历史还在；断线有状态提示 | ⬜ |
| **S5** | 10–11 | 群聊 + 已读回执 | 3 人群聊正常；已读状态各端一致 | ⬜ |
| **S6** | 12 | AI 助手侧车 | 会话里 @AI 能得到回复 | ⬜ |
| **S7** | 13 | 测试收口 + 部署 | **公网地址可访问**；压测数字已记录 | ⬜ |
| **S8** | 14 | 复盘 + 简历 + 面试 | 简历三行数字已填；能 10 分钟口述项目 | ⬜ |

### Definition of Done（每张 Issue 完成的定义）

一张 Issue 只有**同时满足 5 条**才能关闭：

- [ ] 功能按验收条件测过
- [ ] 有对应的单元测试或接口测试（核心逻辑必须有）
- [ ] 代码已合并到 `main`，且 CI 绿
- [ ] 相关文档 / 接口契约已同步更新
- [ ] **我能不看代码讲清这段逻辑**

> 第 5 条最重要。前 4 条是给别人看的，第 5 条是给自己面试用的。

## 五、风险登记表

每两周回顾一次，把变化记下来。

| # | 风险 | 概率 | 影响 | 缓解措施 | 早期信号 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| R1 | **范围失控**，功能越加越多 | 高 | 高 | 严格执行 §3 四条规则 | 连续两周没推进 Must 项 | 监控中 |
| R2 | **AI 写的代码看不懂** | 高 | 高 | 每 Sprint 关掉 AI 重写核心模块；用「10 分钟口述」验收 | 说不出某行代码为什么这么写 | 监控中 |
| R3 | Node 版本导致构建失败 | 中 | 中 | ✅ 已升级到 v22.23.3 并验证 | — | **已消除** |
| R4 | WebSocket 生产环境连不上 | 中 | 高 | Nginx 必配 `Upgrade` + `proxy_read_timeout 300s` | 本地好、线上握手失败 | 未到期 |
| R5 | 磁盘不足导致构建失败 | 高 | 中 | ✅ D 盘 6.08 → 8.84 GB；依赖全部落 C 盘 | — | **已缓解** |
| R6 | 压测数字难看，不敢写 | 中 | 中 | **如实测，不许美化**；数字低就写明条件与瓶颈分析 | 想「稍微改高一点」的念头 | 监控中 |
| R7 | 泄露数据库密码到公开仓库 | 中 | **高** | `.env` 进 `.gitignore`，只提交 `.env.example`；提交前跑敏感词扫描 | 准备 `git add .` 时 | 监控中 |
| R8 | 选型被质疑（Go 岗位少） | 中 | 中 | 保留 Java 关键词 + 投递画像表 + 切换预案 | 投递无人回应 | 监控中 |
| R9 | 笔试过不了，没有面试机会 | 中 | 高 | 第 14 周专门留时间刷题 | 连续两周没刷题 | 监控中 |
| R10 | 中途换技术栈导致返工 | 低 | 高 | 栈已定死；真换只走「切换预案」 | 又想评估别的语言 | 监控中 |

> **R2 是本项目最大的风险，且最隐蔽** —— 因为 AI 会让进度看起来很快：代码在跑、功能在加，但脑子里是空的。**R2 的缓解措施必须每周执行一次，不能攒到最后。**
